### 2.5 需求写法

- 每条需求写明优先级、来源、计划验证方式，以及「给定 … 当 … 则 …」形式的验收标准。任务书要求：**缺少验收标准的需求不算完整的需求。**
- 每个模块文档末尾的追踪矩阵记录每条需求的实现位置（合并请求或代码路径）与状态。需求不得从矩阵中删除；不做的标为「延期」并注明原因。
- 需求变更时同步修改：需求正文、追踪矩阵、该文档的变更记录；涉及决策的同时修改 §7。

| 角色 | 主要模块 | 默认数据范围 | 说明 |
| --- | --- | --- | --- |
| 学生 | M1、M3 | 本人 | 预约座位、签到、报修 |

| 资源管理员 | M2 | 全校 | 整间申请校级终审；撤销已通过的申请 |
| 运营管理员 | M1 | 全校或楼宇 | 只读查看预约情况与统计 |
| 物业调度员 | M3 | 楼宇 | 受理派单、改派、关闭、代验收 |
| 维修人员 | M3 | 楼宇 | 处理派给自己的工单 |
| 物业主管 | M3 | 全校 | 升级工单的接收人、统计 |
| 系统管理员 | 全部 | 全校 | 管理配置、角色、权限、用户；不可删除 |

一个用户可同时拥有多个角色，权限取并集（IAM-ROLE-04）。各模块的权限点见各文档附录 A。

### 4.1 任务书要求的链路

| 编号 | 链路 | 触发 | 效果 | 需求 |
| --- | --- | --- | --- | --- |
| I-1 | M3 → M1 维修下架 | 工单进入「维修中」 | 该室全部座位下架，写入来源 `M3_REPAIR` | M3-INT-01、M1-INT-01、M1-INT-03 |

| I-5 | M2 → M1 回滚 | 驳回、撤回、超时撤销、取消、管理员撤销 | 释放 | M2-INT-01、M1-INT-02 |
| I-6 | 座位状态来源追溯 | 以上任一写入 | 记录来源与来源单号，可按座位与时刻追溯 | M1-INT-06 |

| 编号 | 方向 | 集成点 | 价值 | 优先级 | 需求 |
| --- | --- | --- | --- | --- | --- |
| X-1 | D(SPC) → M1 | 房间、座位、开放时间变更时处理已有预约 | 避免「预约了不存在的座位」 | P0 | SPC-EVT-01、M1-INT-05 |

| X-7 | D(SPC) → M2、M3 | 房间停用、注销时处理在途申请与工单 | 主数据变化不留悬空单据 | P1 / P2 | M2-INT-06、M3-INT-06 |

| X-9 | M1 → M3 | 预约详情页一键报修 | 学生发现故障时的最短路径 | P2 | M1-INT-08、M3-RPT-05 |

暂不实施（不进入基线）：账号停用时自动取消其未开始的预约与申请。

### 4.3 写回约定

- M2、M3 对 M1 座位状态的一切影响，**只**通过 M1 占用块接口（M1-INT-01、02）完成，不直接访问 M1 的数据。
- 写回采用「本地事务 + Outbox + 退避重试」：业务状态变更与待发送的写回消息在同一事务中提交，由投递器异步调用 M1。
- 幂等键为「写入来源 + 来源单号」；重复投递、乱序重放都不产生重复占用块。
- 正常情况下 10 秒内生效；超过最大重试次数仍失败时通知系统管理员，可手动重试（M2-INT-03、M3-INT-03）。

## 5. 附加项：会话代理对各模块的要求

任务书附加项要求通过自然语言会话完成三个模块的主要操作，且「必须通过各模块的公开接口调用」「意图不明确时应追问」。对各模块的要求：

| 模块 | 代理可完成的操作 | 需求 |
| --- | --- | --- |
| M1 | 查询可约座位、创建 / 取消预约、查询预约与历史、查询签到状态 | M1-INT-09 |
| M2 | 检索可申请房间、提交申请、查询申请与审批进度、撤回 / 取消 | M2-INT-05 |
| M3 | 上报故障、查询工单状态与时间线、取消工单 | M3-INT-05 |

- 代理只调用公开接口，不访问任何模块的数据库或内部接口；各模块不为代理提供专用捷径，代理受与 Web 端相同的规则与权限约束。
- 公开接口的错误必须结构化：缺少字段时返回缺失字段名，规则不满足时返回具体规则，资源冲突时返回冲突对象。代理据此追问，例如「我要预约一间教室」→ 接口返回缺少 `date`、`startHour`、`hours`、`buildingId`，代理追问时间与区域。

## 6. 非功能需求（只列影响具体开发的部分）

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-01 | 技术栈 | 选用企业级主流方案，见《架构设计》§9 与 ADR-002 |
| NFR-02 | 环境 | 开发（dev）、测试（test）、生产（prod）三套环境相互隔离：数据库、中间件、配置、密钥各自独立。配置以环境变量注入；镜像与环境无关，同一镜像在 test 验证后晋升到 prod |
| NFR-03 | 容器化与脚本化 | 全部服务与中间件以容器运行；在一台空机器上用一条命令即可拉起任一环境；不依赖人工上机逐条操作 |
| NFR-04 | 流水线 | 提交与合并请求自动触发构建、测试、静态检查；测试失败则后续阶段不执行；合并到主干后自动部署 test；prod 由版本标签触发并经人工审批 |
| NFR-05 | 部署窗口与发布顺序 | test 部署串行（并发锁），部署期间集成测试排队，部署完成且健康检查通过后才运行；发布顺序：数据库迁移 → 公共层 D → M1 → M2 / M3 → 前端 → 代理插件 |
| NFR-06 | 版本与回滚 | 镜像以提交 SHA 标记，发布以语义化版本标签；各服务 `/version` 返回版本号、提交 SHA、构建时间，前端页脚显示版本；回滚即重新部署上一个标签；数据库迁移遵循「先扩展、后收缩」，保证回滚到上一版本时 schema 仍兼容 |
| NFR-07 | 数据演进 | 每个服务以版本化迁移脚本管理自己的 schema，禁止手工改库，空库可一次性重放到最新；种子数据脚本化、幂等、与迁移分离，分为基础数据（所有环境）与演示数据（dev / test） |
| NFR-08 | 一致性与并发 | 同座位同时段不可重复预约，由数据库约束兜底；同一房间同一时段不能并存两个有效整间申请；同一审批级别的并发操作只生效一次；创建类接口支持幂等键；跨模块写回按 §4.3 最终一致；定时任务在多实例下效果恰好一次 |
| NFR-09 | 可测试性 | 时间相关逻辑通过可注入的时钟实现；test 环境提供仅测试可用的「时间推进 / 立即触发调度」能力，prod 禁用；dev / test 的邮件进入邮件沙箱，便于自动化断言；核心规则（M1 的 BR-01 ~ BR-19、M2 的 BR-M2-*、M3 的 BR-M3-*）与三个状态机须经变异测试或「故意破坏实现」验证测试有效 |
| NFR-10 | 安全 | prod 全站 HTTPS；后端每个接口都做权限点与数据范围校验，不依赖前端隐藏；内部接口网络隔离并要求服务凭证；密码加盐哈希；输入校验；登录、签到、上传接口限流；上传文件校验类型与大小 |
| NFR-11 | 隐私（工程伦理） | 个人信息最小化展示：座位状态不对其他学生暴露预约人；房间占用日历不暴露申请人；运营视图与导出默认脱敏；查看完整个人信息的操作写入审计 |
| NFR-12 | 接口规范 | REST + JSON；每个服务提供 OpenAPI 3 描述并纳入版本管理；统一错误结构（错误码、消息、缺失字段或违反的规则、traceId）；时间使用 ISO-8601 带时区；分页参数统一；公开接口路径带版本号 |
| NFR-13 | 可观测性 | 结构化日志；traceId 贯穿网关 → 服务 → 被调服务 → 消息；提供存活 / 就绪健康检查，用作部署门禁 |
| NFR-14 | 性能基线 | 测试环境、数据规模 50 自习室 / 5000 座位 / 5000 学生 / 日 2 万预约 / 1 万整间申请与工单下：座位搜索、申请与工单列表 P95 < 1 秒，创建预约 P95 < 500 毫秒，50 并发用户无错误 |
| NFR-15 | 兼容性 | 学生端移动优先，适配 iOS Safari、Android Chrome 最近两个大版本及桌面浏览器；管理后台（含审批工作台、工单工作台）面向 ≥ 1280px 桌面；屏幕端 1920×1080 横屏全屏 |
