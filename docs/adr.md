# 架构决策记录（ADR）

> 每条决策：背景、决定、考虑过的方案、后果。改变决策时新增一条并标注取代关系，不删旧条目。需求层面的取舍见需求总览 §7（Q1 ~ Q24）。

## ADR-001 粗粒度服务化

- **背景**：任务书要求演示「模块 A 通过网络调用模块 B」，代理只能经公开接口调用，模块组是分工单位。
- **决定**：M1、M2、M3 各一个服务，公共层一个服务；单仓库、单前端；每个环境一个 PostgreSQL，按 schema 与账号隔离。
- **考虑过**：单体（网络调用只能模拟、边界靠自律）；细粒度微服务加注册中心（对 6 人过重）。
- **后果**：模块边界由进程与数据库权限强制；需要处理跨服务一致性（见 ADR-005）。

## ADR-002 技术栈：Python + FastAPI，Next.js

- **背景**：组长决定（2026-10-17）。
- **决定**：后端 Python 3.12 + FastAPI + SQLAlchemy 2（异步）+ Alembic + uv；前端 Next.js 16 + React 19 + TypeScript 5.9 + Tailwind。详见架构 §9。
- **考虑过**：Java + Spring Boot、Vue（初版建议）。
- **后果**：动态类型风险由 mypy strict 与 Pydantic 兜底；同步、异步代码混用的风险由「统一异步」约定与 ruff ASYNC 规则拦截。TypeScript 7 刚发布，暂用 5.9。

## ADR-003 公共层 D 的归属（任务书要求）

- **背景**：任务书要求就公共层归属形成书面决策，说明方案、考虑因素、依据，以及如何达成组内一致。
- **决定**：方案 A。M2 组的 B2 席位负责身份权限与审计（以及暂缓的流水线 X-T02），M3 组的 C2 席位负责空间主数据与通知（以及附加项会话代理 X-T01）。横切能力（公共库、登录鉴权、空间只读、本地环境、前端壳）已在骨架中由组长完成。
- **考虑因素**：
  - 工作量均衡：各席位约 15 ~ 19 个相对点（架构 §10.3）；
  - 契约治理：使用最重的组维护对应公共能力，IAM 与审批角色相关，空间与报修位置、通知与派单提醒相关；
  - 故障归属：按子域划到席位；platform 仍是一个部署单元（ADR-004）；
  - 单点风险：每块至少两人熟悉（同组互审）。
- **考虑过**：方案 B（独立平台组 2 人，M2、M3 各 1 人），因 M2、M3 单人负荷集中且无人互备而未采用。
- **如何达成一致**：组长提出方案并写入本记录与 docs/tasks.md；组员通过「席位认领」Issue 选择席位，全员确认后在此补记确认日期与 Issue 链接。<!-- 确认后填写：日期、Issue 链接 -->

## ADR-004 公共层只有一个部署单元

- **决定**：iam、space、notify、audit 四个子模块打包为 platform-service，按包与 schema 隔离，各有独立 API 前缀。
- **考虑过**：拆成四个服务（多四个进程，部署与发布更复杂）。
- **后果**：已按包与 schema 隔离，日后拆分只是部署层改动。

## ADR-005 跨模块写回：同步 REST + Outbox + 幂等

- **决定**：M2、M3 对 M1 的写回在本地事务中写 outbox，由投递器调用 M1 内部接口；M1 以「来源 + 来源单号」去重；同一 aggregate 按顺序投递。通知、审计、领域事件走 RabbitMQ，同样经 outbox 发出。
- **考虑过**：纯事件驱动（不好演示「网络调用」，也拿不到「取消了哪些预约」的结果）；业务中直接同步调用（M1 宕机会拖垮 M2、M3）。
- **后果**：最终一致，正常 10 秒内生效；失败可见（写回状态）、可人工重放。

## ADR-006 鉴权：服务内验签，IAM 自研 JWT

- **决定**：IAM 签发 RS256 令牌（含角色、权限点与数据范围），各服务经 JWKS 本地验签；网关不做鉴权。签名密钥首次使用时生成并存库。
- **考虑过**：Keycloak（定制数据范围成本高）；网关统一验签（权限校验与业务分离，不便测试）。
- **后果**：权限变更在访问令牌有效期（15 分钟）内生效；私钥存库，生产环境须限制数据库访问。

## ADR-007 学生端为 Web

- **决定**：响应式 Web；二维码指向 Web 签到网址。见需求总览 Q1。

## ADR-008 分支、合并与版本

- **决定**：主干开发；短分支 `<type>/<任务编号>-<短名>`；合并请求至少 1 人批准，生成合并提交；里程碑后在 main 打附注标签 `vX.Y.Z` 并生成发布说明。
- **后果**：提交历史可按任务与需求追溯；发布内容可由两个标签之间的提交得出。

## ADR-009 M2 写入 M1 的时机

- **决定**：提交即 HOLD，终审通过升级 ACTIVE，驳回、撤回、超时、取消即释放。见需求总览 Q6。

## ADR-010 M3 图片附件存挂载卷

- **决定**：附件文件存 repair 服务的挂载卷，元数据入 m3 schema；不引入对象存储。见需求总览 Q24。

## ADR-011 前端静态导出

- **决定**：Next.js `output: "export"`，由 Nginx 托管；前端不写业务逻辑，详情页用查询参数传 ID。
- **后果**：生产无需 Node 运行时；不能用服务端渲染与运行时动态路由。

## ADR-012 契约以代码为源

- **背景**：既要「契约先行」，又不想手写一遍 OpenAPI 再写一遍代码。
- **决定**：契约 = 接口桩的签名与 Pydantic 模型（跨服务模型在 `campus_common/contracts`）；`make contracts` 导出到 `contracts/` 并生成前端类型；`make contracts-check` 防止代码与契约漂移。
- **后果**：骨架阶段已为全部 138 个待实现接口写好桩；修改契约须走评审（AGENTS.md §4.3）。

## ADR-013 前端令牌存 localStorage

- **决定**：访问令牌与刷新令牌存 localStorage，快过期时自动刷新。
- **考虑过**：httpOnly Cookie（需要网关或后端改造会话处理）。
- **后果**：刷新页面仍保持登录；XSS 风险由「不渲染未转义的用户输入」约束缓解。
